# Square World Generation V3 — архитектура

## Уточнение 0.5: безопасный коридор и городской портал

`square-v5` сохраняет ту же слоистую модель, но ужесточает публикацию дорог. Перед записью расширенного дорожного профиля проверяется весь коридор, включая боковые полосы, а не только centerline. Клетки committed task footprints являются hard obstacle. После фильтрации публикуется только та часть нового коридора, которая четырёхсвязно присоединена к существующей сети; отдельные дорожные острова отбрасываются.

Межгородской A* заканчивается в portal-клетке непосредственно снаружи исходного `100×100` city bounds и обязан обходить сам город. От portal до gateway строится короткий контролируемый ортогональный сегмент `HIGHWAY`, а дальше начинается `ARTERIAL`. Поэтому трасса не может случайно прорезать будущие районы. Здание разрешается разместить только в позиции с расстоянием до опубликованной дороги не более двух клеток.

Контрольный fixture версии: три города, по три района и 30 задач. Его инварианты проверяет `npm run test:review-worldgen`, устойчивость на разных картах — `npm run test:review-worldgen:soak`.

## Уточнение 0.4: иерархия городских дорог

Городские дороги разделяются на три независимых уровня построения:

1. `HIGHWAY` соединяет существующую дорожную компоненту только с gateway нового города.
2. `ARTERIAL/COLLECTOR` соединяет gateway с компактным hub и входами районов.
3. `LOCAL` строится только прямыми ортогональными сегментами внутри envelope района: главная улица и короткие ветви.

A* применяется только к внешнему connector, учитывает воду, рельеф и committed footprints. Внутренние улицы не используют стоимость уже существующих дорог: это исключает уход улицы к далёкому шоссе и случайные ступенчатые петли. Расширение района добавляет локальный spine в новой области и присоединяет его к ближайшей дороге одним connector.

## Уточнение 0.4: область камеры

Клиент вычисляет доступную область как union всех city bounds, расширенный на фиксированную природную рамку. Это не меняет бесконечную детерминированную функцию мира: ограничение относится только к текущему опубликованному viewport. После создания нового города bootstrap расширяет рамку. Chunk range считается из реальных углов экрана и дополнительно расширяется на `0.75` ширины/высоты viewport; позиция камеры clamped так, чтобы экран всегда оставался внутри рамки.

## Уточнение 0.4: рельеф

Природный слой остаётся чистой функцией `(seed, x, y)`. Domain-warped lake fields формируют несколько связных бассейнов, отдельное elevation field создаёт `HILL/MOUNTAIN`, а canopy field вырезает поляны внутри влажных лесных массивов. Крупные формы читаются terrain tiles, силуэт усиливают редкие props, размещённые детерминированно и исключённые из road/task occupancy.

## 1. Термины и доменная модель

| Игровая сущность | Управление работой | Ответственность |
|---|---|---|
| `Country` | Project | seed, версия генератора, бесконечное пространство, макрограф объектов |
| `City` | Epic / subproject | территория, ворота, дорожный граф, районы и стиль |
| `District` | Sprint | граница, каркас улиц, участки, сектор роста и lifecycle |
| `Building` | Task | footprint, участок, тип, стадия строительства и task metadata |

В API и базе сохраняются явные имена `country/city/district/building`. Интеграционные поля `externalProjectId`, `externalEpicId`, `externalSprintId`, `externalTaskId` задают соответствия, но не подменяют доменные сущности.

## 2. Почему нужна слоистая модель

Клетка не должна содержать один взаимоисключающий enum. Один экран собирается из слоёв:

1. `BaseMaterial`: grass, meadow, sand, wet_sand, clay, stone, shallow_water, deep_water.
2. `TerrainEdge`: берег, переход материала, волна, обрыв.
3. `Infrastructure`: асфальт, тротуар, тропа, бордюр, мостовая боковина.
4. `Parcel`: участок/платформа здания, районная граница, reservation.
5. `Object`: здание, дерево, фонарь, столб, остановка, автомобиль, цветы.
6. `UI`: выделение района, статус задачи, hover/selection.

Так дорога поверх травы, мост поверх воды и здание поверх асфальтовой платформы используют одни и те же 8×8 элементы без комбинаторного множества тайлов.

## 3. Координаты, чанки и бесконечность

### 3.1 Координаты

```ts
type Cell = { x: number; y: number };
type ChunkCoord = { x: number; y: number };
type LocalCell = { x: number; y: number }; // 0..63
type ConnectionMask = number; // N=1, E=2, S=4, W=8
```

Соседство планирования — 4-way. Для сглаживания биомов, декора и расчёта расстояния может использоваться 8-way, но диагональ не создаёт дорожное соединение.

`chunk = floorDiv(cell, 64)`, `local = floorMod(cell, 64)`. Обычное JS-деление с усечением не подходит отрицательным координатам.

### 3.2 Уровни генерации

| Уровень | Размер по умолчанию | Что хранит |
|---|---:|---|
| Cell | 8×8 px | слои рендера и occupancy |
| Chunk | 64×64 cells | сетевой/DB snapshot и кэш |
| Feature region | 512×512 cells | реки, озёра, леса, трассы; halo ≥128 |
| Country | бесконечный | seed, версии, реестр опубликованных features |

Страна никогда не увеличивает массив. Увеличиваются `generated bounds` и набор материализованных чанков. Клиент запрашивает viewport и один кольцевой prefetch.

### 3.3 Seed-потоки

Каждая подсистема получает независимый поток:

```text
hash(countrySeed, generatorVersion, "terrain", x, y)
hash(countrySeed, generatorVersion, "hydrology", regionX, regionY)
hash(countrySeed, "city", cityId)
hash(citySeed, "district", districtId)
hash(districtSeed, "task-placement", taskId)
```

Добавление задачи не меняет деревья другого района. Идентификаторы сущностей входят в seed; номер вызова общего PRNG — нет.

## 4. Генерация страны и природы

### 4.1 Базовые поля

Высота, влажность и температура вычисляются как непрерывные глобальные поля из нескольких октав OpenSimplex2/Value noise. Низкочастотный domain warp убирает прямые и круглые границы. Материал определяется не одним порогом, а таблицей `height × moisture × distanceToWater × localVariation`.

Noise отвечает только за форму и вероятности. Он не гарантирует связные реки, дороги и доступность, поэтому после него работают графовые планировщики.

### 4.2 Гидрология

1. В feature region с halo сэмплируется coarse elevation grid.
2. Priority-Flood/flow preprocessing устраняет непреднамеренные цифровые ловушки и даёт направления стока.
3. Детерминированные источники выбираются на возвышенностях с минимальной дистанцией.
4. Потоки трассируются по accumulated flow; значимые сливаются в river feature с устойчивым `featureId`.
5. Явно выбранные бассейны становятся озёрами; морфологическая очистка удаляет одиночные пиксели и узкие артефакты.
6. Shared-edge key определяет порты пересечения границы макрорегионов. Соседние регионы обязаны принять одинаковые порты.
7. Чанк только растеризует feature graph, поэтому порядок его генерации не меняет русло.

Публикуется не миллион водяных клеток как первичная модель, а полилиния/полигон feature плюс кэш растеризации. Локальные overrides сохраняют результат мостов и ручных изменений.

### 4.3 Леса и декор

Лес — кластерный feature из suitability field, а не независимый шанс каждой клетки. Деревья размещаются Poisson-like выборкой внутри маски леса, с меньшей плотностью у дороги и воды. Цветы, камни и кусты являются детерминированным декором и могут быть удалены при строительстве без изменения base material.

## 5. Города и межгородская сеть

### 5.1 Площадка города

Начальная область — 100×100 клеток. Вокруг неё резервируется `growth envelope` (стартовый ориентир 192×192). Минимальное расстояние центров считается от резервов и транспортного коридора, а не задаётся магическим числом; стартовый диапазон 288–384 клетки проверяется визуально и нагрузочно.

Кандидаты площадок генерируются Poisson-disc, затем оцениваются:

```text
siteScore =
  + flatness
  + buildableRatio
  + scenicWaterBonus
  + connectionEase
  + expansionCapacity
  - floodRisk
  - protectedFeatureCollision
  - otherCityReserveCollision
```

Первый город получает `country gateway` за видимой областью, и трасса входит в город с края загруженного мира. Следующий город выбирается не на одной линии, а среди нескольких пригодных кандидатов.

### 5.2 Национальный граф дорог

1. Узлы — ворота городов и существующие junction nodes.
2. Delaunay/k-nearest создаёт небольшой набор разумных кандидатных рёбер.
3. Minimum spanning tree гарантирует связность всех городов.
4. 10–25% рёбер добавляются обратно по detour score, чтобы сеть имела петли и не выглядела деревом.
5. Coarse A* выбирает коридор; detailed A* прокладывает клетки.

Road edge хранит абстрактную centerline и `profileId`, а не единственную асфальтовую клетку. После поиска пути corridor rasterizer разворачивает профиль поперёк линии:

| Профиль | Ориентировочная полная ширина | Применение |
|---|---:|---|
| pedestrian path | 1–2 клетки | парк и короткий доступ |
| local street | 4 клетки | две полосы/края квартала |
| collector | 6 клеток | основная дорога района, остановки |
| arterial | 8 клеток | ворота города и межрайонная связь |

Числа калибруются визуально, но остаются кратны одной клетке. Detailed A* проверяет clearance всего профиля, а не только centerline. Перекрёсток — объединение растеризованных corridors; curb строится по внешней границе получившейся asphalt mask.

Стоимость detailed A*:

```text
cost = distance
     + slopePenalty
     + waterCrossingPenalty
     + forestPenalty
     + cityReservePenalty
     + turnPenalty
     - existingRoadReuseBonus
     - preferredBridgeSiteBonus
```

T-перекрёсток появляется при присоединении к существующему ребру. Дорожная маска вычисляется из четырёх соседей; отдельный sprite перекрёстка не нужен. Мост допускается только на коротком валидном пролёте между двумя берегами с прямыми подходами; длинный водный обход обычно дешевле.

### 5.3 Городская сеть

До районов город получает:

- 1–2 ворота;
- основную arterial дорогу между воротами/центром;
- несколько зарезервированных collector-направлений;
- свободные growth sectors между ними.

Улицы создаются road grammar с ограничениями, а не одной случайной линией. Внутренняя сеть получает и прямые кварталы, и повороты, но каждый новый сегмент обязан давать полезный frontage или соединение.

## 6. Район как расширяемый план

### 6.0 Проверенные альтернативы

Диагностический симулятор `scripts/worldgen-algorithm-study.ts` прогнал по 300 seed для трёх вариантов при абстрактном ядре 108 клеток и одинаковом наборе прямоугольных участков. Его одноклеточная дорога обозначает centerline, а не финальную ширину road profile:

| Подход | Доступно от дороги | Успех участков | Tendrils | Уникальные планы |
|---|---:|---:|---:|---:|
| Rectangle + straight road | 42.9% | 90.8% | 0.0% | 1.3% |
| Free polyomino + path | 43.8% | 79.0% | 6.4% | 100.0% |
| Road-first hybrid | 78.5% | 97.3% | 0.4% | 99.7% |

Это не production-бенчмарк и не моделирование воды/конкуренции. Он подтверждает только базовый выбор формы и участков: свободный polyomino слишком часто создаёт неудобные края, а прямоугольник не даёт достаточной вариативности. Полные результаты и пример находятся в `proof/district-algorithm-report.md` и `proof/district-algorithm-samples.svg`.

### 6.1 Размер района

Число `30 клеток` нельзя использовать как полную площадь района. В текущем asset manifest один крупный footprint занимает до `6×5 = 30` клеток, а одна collector-улица имеет ширину около 6 клеток. Поэтому 30 допустимо только как минимальный ранний резерв земли под здания. Хранятся два бюджета:

- `grossCells`: вся граница района, включая улицы, тротуары и парк;
- `buildableCells`: сумма участков под задачи.

Размер вычисляется:

```text
grossTarget = max(minDistrict,
  ceil(expectedLotArea * 1.35 + roadCorridorArea + publicSpaceBudget))
```

Если задачи ещё неизвестны, `expectedLotArea` прогнозируется из capacity SP и распределения footprints каталога. Стартовые ориентиры: 80–140 gross cells только для микрорайона с 1–3 небольшими задачами; 160–320 для обычного спринта; крупный район может занять больше. Реальные значения калибруются на фактических задачах и не ограничиваются жёстким максимумом.

### 6.2 Создание

Планировщик строит 8–32 кандидата:

1. Выбирает seed возле collector/arterial и свободный growth sector.
2. Строит дорожный скелет: короткая петля, L/T-ветвь или две параллельные улицы.
3. Выращивает связную polyomino-границу вокруг сети.
4. Разбивает frontage на скрытые участки размеров каталога.
5. Резервирует тротуары, парк/площадь, остановку и декор.
6. Проверяет связность, компактность, отсутствие дыр и одноклеточных хвостов.
7. Выбирает лучший валидный кандидат с novelty penalty относительно прошлых районов.

### 6.3 Состояния клеток

```text
NATURAL  -> RESERVED -> COMMITTED
                   \-> RELEASED
```

- `NATURAL`: мир ещё не занят городским планом.
- `RESERVED`: скрытый участок, будущая улица или парк; можно перепланировать локально.
- `COMMITTED`: уже показанный пользователю объект; обычный генератор не меняет.
- `RELEASED`: резерв освобождён и может стать природой/новым планом.

Lifecycle района: `PLANNED → ACTIVE_MUTABLE → SEALED`. В городе одновременно только 1–2 `ACTIVE_MUTABLE`; каждый имеет непересекающийся `growthSector` и `accessCorridor`.

### 6.4 Расширение без разрушения города

Если новая задача не помещается:

1. Подобрать другой свободный скрытый участок/rotation.
2. Объединить совместимые соседние reserved lots.
3. Открыть зарезервированную ветвь улицы и прилегающие участки.
4. Присоединить лучший frontier patch только внутри growth sector.
5. Продлить collector и city envelope, если сектор упёрся в границу города.
6. Вернуть `PLACEMENT_BLOCKED` с диагностикой, если валидного варианта нет.

Перепланировать можно только `RESERVED`. Границы `COMMITTED` и всё внутри `SEALED` входят в hard constraints. Это устраняет скачки дорог и зданий после каждой задачи.

## 7. Задачи и здания

### 7.1 От оценки к классу участка

Оценка задаёт предпочтительный класс, но конкретный footprint берётся из manifest:

| Estimate | Типовой диапазон участков |
|---:|---|
| 1 | 2×2, 3×2 |
| 2 | 3×2, 3×3 |
| 3 | 4×3, 5×3 |
| 6 | 6×4, 7×5 или составной объект |

Маленькая задача может получить группу 2–3 декоративных зданий только если manifest объявляет это единым `buildingVariant`; бизнес-сущность всё равно одна.

### 7.2 Выбор здания и позиции

1. NLP/правила извлекают task tags: residential, retail, transport, health, safety и т.д.
2. Каталог фильтруется по estimate, footprint, allowed terrain, district style и city quotas.
3. Перечисляются все валидные участки и rotations.
4. Для каждой пары считается score:

```text
fit + roadFrontage + pedestrianAccess + semanticMatch
+ cityNeed + districtSynergy + visualDiversity
- rareBuildingDuplication - awkwardGap - terrainConflict
```

5. Выбор выполняется seeded-random среди top-K, а не всегда берётся максимум.
6. В БД сохраняются выбранный вариант, seed, score breakdown и revision для воспроизведения.

### 7.3 Строительство

`planning`, `started`, `in_progress`, `testing`, `done` отображаются в 5 стадий. Процент уточняет стадию внутри статуса, но не перемещает footprint. Здание, платформа и anchor стабильны от фундамента до готового вида.

## 8. Уникальность без хаоса

Каждая страна, город и район получают `StyleDNA`:

```ts
type StyleDNA = {
  density: number;
  gridRegularity: number;
  roadCurvature: number;
  averageSetback: number;
  vegetation: number;
  commercialRatio: number;
  publicSpaceFrequency: number;
  waterAffinity: number;
  paletteId: string;
};
```

Для кандидата вычисляется fingerprint: гистограмма типов дорог, размеров кварталов, footprints, видов зданий, плотности зелени и формы границы. Сходство с уже опубликованными районами добавляет штраф. При этом hard constraints всегда важнее novelty.

## 9. Детерминированный rule engine без ИИ

В runtime нет LLM, prompt, embedding или внешнего генеративного API. Семантика задачи определяется явным `buildingHint` и локальным словарём тегов; при отсутствии подсказки каталог фильтруется и ранжируется детерминированно.

Разнообразие обеспечивают:

- versioned building catalog;
- `tags`, `roles`, estimate bands и category quotas;
- `maxPerCity`, `maxPerDistrict`, prerequisites и incompatibilities;
- city/district `StyleDNA` из seed;
- top-K seeded selection среди только валидных вариантов;
- независимые decoration и terrain seed-потоки.

Новый тип поведения добавляется зарегистрированным rule handler по стабильному `ruleId`. Каталог остаётся данными; неизвестный `ruleId` является ошибкой asset validation, а не молчаливым fallback.

## 10. Персистентность и конкуренция

Целевая БД — PostgreSQL + PostGIS. Дискретная occupancy остаётся на integer `x/y` с уникальными B-tree индексами; PostGIS используется для bounding-box запросов, полигонов city/district envelopes, русел, озёр и GiST spatial index. Это не превращает клеточный solver в GIS-зависимый код: domain работает с собственными `Cell/Rect/Polyline`, а adapter выполняет сериализацию геометрии.

### 10.1 Основные таблицы

- `countries`, `cities`, `city_envelopes`, `city_gates`;
- `world_features`, `feature_regions`, `terrain_chunks`, `chunk_revisions`;
- `road_nodes`, `road_edges`, `road_cells`;
- `districts`, `district_cells`, `growth_sectors`;
- `lots`, `lot_cells`, `buildings`, `building_cells`, `decorations`;
- `generation_jobs`, `generation_revisions`, `generation_decisions`;
- `outbox_events`, `idempotency_keys`.

Уникальный индекс occupancy запрещает двум committed-объектам владеть одной клеткой/слоем. Большие наборы клеток сохраняются батчами в одной транзакции.

### 10.2 Команды

`CreateCity`, `CreateDistrict`, `AddTask`, `ExpandDistrict` создают generation job с idempotency key. Worker:

1. читает текущую revision;
2. ставит advisory lock на city/district;
3. строит кандидаты вне транзакции;
4. повторно проверяет revision;
5. атомарно сохраняет выбранный план и outbox events;
6. при конфликте пересчитывает на новой revision.

## 11. WebSocket и клиент

HTTP возвращает authoritative chunk snapshot. WebSocket передаёт только versioned события:

- `city.generated`;
- `district.generated` / `district.expanded` / `district.sealed`;
- `building.placed` / `building.stage_changed`;
- `road.changed`;
- `chunks.invalidated`.

Событие содержит `countryId`, `revision`, bounding box и affected chunk keys. При пропуске revision клиент не применяет дельту вслепую, а перезапрашивает snapshot. Рендер использует atlas, culling и object pooling; UI-выделение района — отдельный overlay, а не часть terrain sprite.

## 12. Диагностика

Каждая генерация сохраняет:

- входной seed и generatorVersion;
- hard constraints;
- число кандидатов и причины отбраковки;
- score breakdown победителя;
- изменённые клетки по состояниям;
- timings по фазам.

Debug endpoint умеет воспроизвести revision и выгрузить JSON/SVG-план. Это обязательная часть, иначе редкие дефекты мира невозможно расследовать.

## 13. Предлагаемые ADR после подтверждения

1. Square grid 8×8 replaces axial hex coordinates.
2. Infinite lazy world with feature regions and deterministic edge contracts.
3. Committed/reserved/natural cell ownership and sealed district invariants.
4. Hybrid district planner instead of whole-area regeneration or global WFC.
5. No runtime AI; catalog and registered deterministic rules are the only planning authority.

До принятия этих ADR новый генератор существует как `generatorVersion = square-v3`. Тестовые hex-миры можно пересоздавать; мир с реальными данными не конвертируется изменением координат на месте, а остаётся read-only до отдельного export/import процесса.
