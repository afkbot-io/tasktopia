# Проверка продолжения задач между спринтами

Задача Tasktopia85. Локальная проверка21.11.2026: Node24.15.0,
PostgreSQL16.14, сборка1.29.0. Точная ревизия, обязательный CI и результат
публикации фиксируются в связанной задаче и PR.

## Проверенное поведение

- Единственные ID/номер и основной участок сохраняются через три спринта.
  Площадки имеют собственную геометрию/вход, ссылаются на каноническую задачу,
  не расходуют номер следующей задачи и сохраняются при rebuild.
- Этапы CARRIED не меняют свои показатели после завершения задачи. Отчёт,
  список района и workload различают переданную/выполненную работу; SP
  завершения учитываются один раз. World audit чист после передачи и удаления.
- Конкурентные передачи из одного исходного спринта дают один успех.
  Отказ записи участка откатывает всё. Повтор/reconnect не создают этап повторно.
- Реальный SDK проверяет initialize/tools, строгие схемы, scope/роль/страну,
  ограничения состояний, принятую фоновую операцию и polling. Прежний worker
  не захватывает CONTINUE_QUEUED. HTTP предоставляет только GET истории.
- Заполненная схема0049 обновляется без изменения строк задач, размещений и
  audit history; прежняя вставка без work_district_id остаётся допустимой.
  Guard отката разрешает старый reader только до первого продолжения/job и
  отказывает при неизвестном состоянии проверки.
- Смешанные writers проверяются на уровне БД: прежний SQL перенос не меняет
  основной район, прямое удаление района или предварительное удаление его задач
  отклоняется. Явные новые команды удаления задачи/города и каскад страны
  сохраняют ожидаемое поведение. Регрессия сначала воспроизвела сдвиг основного
  здания прежним SQL, затем проверяет отказ и сохранность цепочки.

Локальные наборы:20 проверок сервиса/MCP/пагинации;51 проверка чтения и runtime;
45 успешных затронутых регрессий до исправления двух устаревших migration
fixtures; затем7/7 проверок миграции/цепочки/масштаба и96/96 регрессий чтения,
документов, кэша, миниатюр и release guard. Это пересекающиеся наборы, их
количества не складываются в общий итог. `npm run lint`, `npm run build`
(включает typecheck) и `git diff --check` завершились успешно.

## Настоящий браузер

`tests/e2e/sprint-continuation.spec.ts`:5/5, Chromium, Firefox, Desktop WebKit,
Pixel7 и iPhone13. Продолжение и смена статуса выполняются через реальный HTTP
MCP; появление площадки/прогресса проверяется по WebSocket без reload.
Сценарий проверяет пустую историю, клавиатуру/касание,503 и повтор, одну карточку,
неизменную камеру, сохранённый canvas и отсутствие HTTP write/console errors.
После удаления проверено пояснение архивной площадки. Скриншоты истории и
мира просмотрены: прежние forest/brass UI и нативный компактный спрайт,
без растяжения, горизонтального переполнения и новых команд изменения в UI.

При диагностике исправлены неверное определение текущего спринта в compact
чтении и обработка клика по площадке удалённой задачи. Жест QA ограничен
размером окна, как в существующих map-тестах, чтобы не уходить за окно Firefox.
Все пять итоговых прогонов выполнены после этих исправлений.

## Масштаб и границы измерения

`tests/task-sprint-scale.test.ts`, отдельный последовательный прогон:

| Нагрузка | Результат |
| --- | --- |
| Настоящая сцена200 задач после продолжения |12 chunks, холодная подготовка201мс;200 канонических задач и одна площадка; история не вложена в scene |
| История + список + workload,200 задач |3 SQL на выборку; пять замеров15/12/10/12/11мс |
|10 000 задач и20 000 этапов |3 SQL на выборку;76/64/66/62/66мс; страница50 записей, история1 запись, менее3KB |

10 000 — изолированный workload метаданных PostgreSQL, без генерации
10 000 новых зданий и без утверждения о FPS такого города. В этом изменении
не менялись бюджеты существующего большого города. Браузерная проверка
телефонов — эмуляция, не физические устройства. На общем сервере нагрузочные
фикстуры не создаются. Первая история создаётся при продолжении; для
импортированных/прежде физически перенесённых задач прошлые проценты не
восстанавливаются предположениями.

## Приёмка и восстановление

Через MCP начать задачу, выполнить часть работы, вызвать task.continue с
ожидаемым fromDistrictId; отдельно закрыть исходный и активировать следующий
район. Проверить основной участок, обе площадки, вкладку «Спринты», фильтр и
финальные SP. Не выполнять этот сценарий в личных данных без намерения их менять.

Миграция расширяющая, перегенерация не требуется. После первого продолжения
старый runtime несовместим; updater запрещает image-only rollback и сохраняет
совместимый кандидат для исправления вперёд. Штатные backup/lock/health/static
gates остаются обязательными; план восстановления — в DEPLOYMENT.md.
