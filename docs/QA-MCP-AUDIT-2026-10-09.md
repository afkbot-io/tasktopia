# Полная локальная проверка MCP — 2026-10-09

Проверен MCP Tasktopia целиком: каталог, схемы, оба протокола, авторизация,
доменные изменения, хранение файлов и доставка изменений в игру.
База аудита `545a0de10c646e28267cb9f62e3034270c912bd2`, ветка
`codex/city-everyday-events`. Исходные файлы и собранный сервер закреплены
SHA-256 в [receipt](evidence/mcp-audit-2026-10-09/summary.json).
Пользовательская рабочая копия, рабочие страны и сайт не изменялись.

## Исправленные дефекты

1. Повтор загрузки с тем же ключом и другими байтами той же длины возвращал старый файл. Теперь запрос сравнивает SHA-256 содержимого и возвращает `CONFLICT`. Старый receipt обновляется только после проверки реального файла, без дубля, нового события или увеличения версии мира. Недоступный старый файл отклоняет повтор.
2. `Buffer.from(..., "base64")` молча пропускал посторонние символы. MCP теперь проверяет полный стандартный Base64, padding, длину строки и декодированный лимит. Пустые, повреждённые, `data:` и слишком большие файлы отклоняются до записи.
3. Загрузка оставляла файл после rollback; удаление отдельного вложения уничтожало файл даже при rollback. Очистка загрузки привязана к rollback, удаления — к commit.
4. Удаление задачи, района или города оставляло файлы каскадно удалённых вложений. Их пути собираются в той же транзакции и очищаются после commit; rollback сохраняет файл и строку.
5. Ключ, ошибочно переданный в query URL `/mcp`, попадал в access log. Вся query-строка этого endpoint теперь скрывается, включая закодированные имена параметров. Query-ключ по-прежнему не авторизует запрос.

Обновлены контракт, публичная AI-инструкция, skill и changelog. Устранены
устаревшие указания на форму переноса в UI: рабочие изменения выполняются через
MCP. Сам transfer освобождает прежний участок; постоянные руины остаются после
delete. Предварительная гипотеза о постоянной площадке MOVE была опровергнута
актуальным кодом и не включена в изменения.

## Границы и доказательства

- Настоящий Fastify listener, SDK client 2.2.0, server 2.0.0, PostgreSQL с отдельной временной схемой и каталогом uploads. Современный MCP и legacy `2025-11-25`, initialize, tools/resources/templates, отсутствие несуществующих capabilities и удалённых selected-country tools.
- Все шесть scopes проверены независимо по полной группе инструментов. `city.get` требует оба read scopes; VIEWER с сохранёнными write scopes своей страны не может писать в чужой доступной стране. Отзыв членства действует на следующем запросе существующего клиента.
- Явная страна независима от выбранной в UI. Чужая страна, task UUID и resource отклоняются без раскрытия данных. Исполнитель первого STARTED — владелец токена; последующее назначение сохраняется. Подмена actor не принимается.
- GET/POST/DELETE: Bearer challenge, неправильный Origin, отсутствующий/истёкший/отозванный ключ, повреждённые scopes, ротация, отказ cookie/query/X-API-Key. Настоящий route limit: первые 90 неавторизованных запросов отклоняются как 401, следующий — 429.
- Различные payload с одним ключом возвращают `CONFLICT`. Четыре параллельных одинаковых комментария создают ровно одно событие; два разных конкурентных payload — одно изменение и один конфликт. Переподключение сохраняет идемпотентность.
- Некорректная стадия, подтверждение удаления, чужой исполнитель, traversal Markdown, повреждённый/слишком большой файл, ошибочные HTTP envelopes, неизвестные tools/resources: состояние не меняется. Internal error не раскрывает исходное сообщение. После timeout и reconnect чтение работает.
- Фоновая генерация города, района и задачи проходит HTTP → `accepted` → настоящий worker → polling COMPLETED → повтор без нового job. `task.create` добавляет URL и workload к DTO; polling возвращает сам актуальный DTO, поэтому проверяется сущность с учётом этого различия.
- Живой Chromium, два клиента: AIR/RAIL/PORT возвращаются из TESTING в работу, завершаются и удаляются через MCP. Оба браузера получают новые реальные scene DTO через WebSocket; повтор не создаёт событие, удалённые терминалы исчезают из направлений. Page errors отсутствуют.

## Повтор и пределы

Из этой рабочей копии, Node24 и тестового PostgreSQL на localhost:55433:

```sh
TEST_DATABASE_URL=postgres://tasktopia:tasktopia@127.0.0.1:55433/tasktopia_test npx vitest run tests/mcp-http-contract.test.ts tests/task-extras.test.ts tests/task-share-preview.test.ts
TEST_DATABASE_URL=postgres://tasktopia:tasktopia@127.0.0.1:55433/tasktopia_test npm test
npm run lint
npm run build
```

Built smoke запускается только против своей локальной QA-БД и своего
пользователя. Для повторного live сценария подготовить peer terminals по
инструкции транспортной приёмки: тест намеренно удаляет их. Не применять
эти команды к рабочим данным.

Новых миграций и зависимостей нет. Обновление старого attachment receipt
происходит при доказанном одинаковом повторе; старый бинарник после возврата
может отклонить такой уже обновлённый ключ, данные при этом сохраняются.
Отмена HTTP не отменяет уже принятую фоновую работу. Проверены обычные
commit/rollback; SIGKILL и неисправность файловой системы не моделировались,
физическая очистка остаётся асинхронной. Это локальная квалификация и AI-review,
а не SCM approval или подтверждение выкладки. Сайт не публиковался.
