## Порядок задач при перегенерации

`REGENERATION_FORCE=1` обязателен: без него audit-clean страны пропускаются.
SQL читает задачи по `task_number,id`, компилятор обрабатывает новые размещения
численно по taskNumber, сохраняя привязку задачи к её району. Поддерживаются
совместимые размеры и инфраструктурные резервы; это не обещание географического
порядка каждого дома слева направо.

При наличии постоянных MOVE/RUIN текущая регенерация сохраняет прежнюю топологию
и живые размещения целиком. Это ограничение нужно учитывать при последующих
релизах. В проверенной production-схеме до `0021` таблиц permanent sites ещё
нет, поэтому оно не препятствует первому пересозданию текущих миров.

Контракт `managed-release` прямо запрещает менять receipt, policy, credentials
или deployment scripts во время релиза ради прохождения заблокированного плана.
Поэтому автоматическая установка/копирование receipt или обход валидатора не
выполнялись. Требуется корректно подготовленная управляемая рабочая копия
оператором проекта. `builder release validate` ещё не выполнялся; ready-результата
нет. Merge, deployment, миграции и перегенерация не выполнялись.

После устранения этой причины: точный release item → curated commit/PR и merge
→ проверка amd64-кандидата → проверенный production backup/restore → валидный
release manifest → maintenance cutover и FORCE replay всех 10 миров с новым
актуальным baseline → conservation/world audit/smoke → открытие трафика.
Следовать [runbook](COMPACT-PRODUCTION-RUNBOOK.md), не обычному image-only update.
