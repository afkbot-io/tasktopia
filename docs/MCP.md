# MCP и API

Production endpoint: `https://tasktopia.online/mcp`. Транспорт — Streamable HTTP. Сервер использует актуальный MCP `2026-07-28` и принимает stateless-клиенты `2025-11-25` в режиме совместимости. `POST` передаёт JSON-RPC, а `GET`/`DELETE` обслуживаются транспортным lifecycle.

Самодостаточная публичная инструкция, которую можно передать ИИ без доступа к репозиторию: [https://tasktopia.online/ai.md](https://tasktopia.online/ai.md).

Готовый Codex skill для выбора проектного контекста, постановки задач и ведения прогресса: [https://tasktopia.online/skills/tasktopia-progress/SKILL.md](https://tasktopia.online/skills/tasktopia-progress/SKILL.md). Установка и правила вызова приведены в публичной AI-инструкции.

## Внутренний API обзорной карты

### Общественные пространства и рост спринта

MCP `task.create` принимает описание работы без выбора размера или типа здания.
Сервер сначала занимает подходящий свободный участок существующего квартала
текущего района, затем подбирает дом или общественное пространство под участок.
Параметры `buildingHint`, `visualKind` и `parkVariant` отклоняются.
Оценка задачи описывает объём работы и не задаёт размер здания.

Новый квартал появляется, когда в существующих кварталах района нет подходящего
места. Перенос освобождает прежний участок; история переноса остаётся в задаче.
Старые записи MOVE сохраняются в базе как история и больше не занимают землю
и не отображаются. Руины удалённых задач остаются историческими объектами.

### Уровни карты

Уровень планеты загружается через аутентифицированный браузерный
`GET /api/planet-atlas`. Контракт `schemaVersion: 5` возвращает только доступные
текущему пользователю страны и компактные агрегаты: количество городов,
районов, всех и незавершённых зданий и общий прогресс. Передаются канонические
границы мира, центры городов/районов и действующие task-аэропорты. Клиент
строит общую географию из этих данных и `planetSeed`; материки определяются
четырёхсвязными группами суши. Ответ приватный, использует ETag и `Cache-Control: private,
no-cache`; клиентский snapshot хранится отдельно
для каждого `userId`. Переименование страны, изменение состава или прогресса
меняет revision и ETag. Это внутренний UI endpoint, а не MCP resource.

Аутентифицированный браузер получает обзор страны через
`GET /api/countries/:countryId/overview`.
Это не MCP resource и не замена `country.get`/`city.list`: endpoint
предназначен только для UI. Контракт `schemaVersion: 8` содержит `terrainSeed`,
ограниченную сетку terrain/ownership с явно переданными dimensions и cellSize,
города с исходными и обзорными центрами, агрегаты
районов и semantic miniatures. Полная городская геометрия, задачи,
surfaces, props и sprite URL в ответ не входят. Один квартал представлен одним
миниатюрным зданием; аэропорты передаются отдельно. `connections` описывает
логические воздушные связи, а не готовые межгородские дороги.

`groundRoads` отдельно содержит компактные реальные дорожные коридоры.
`railConnections` и `seaConnections` используют идентификаторы готовых
терминалов и согласованные offset расписания; `transportPeers` сообщает только
наличие доступного второго терминала для объяснения отсутствия коридора.
PLANET передаёт авторизованные `airRoutes`/`railRoutes`/`seaRoutes`, а страны — сохранённые
AIR/RAIL сети. Недоступные названия, остановки и геометрия не публикуются.

`GET /api/countries/:countryId/cities/:cityId/scene` публикует CITY schema 5:
все resident DETAIL chunks одним ответом, `airports` с планом или `NO_AIRFIELD`,
локальную ЖД, порты и готовые транспортные связи. Кеш ключуется пользователем,
географией и версией; новый клиент требует CITY 5 и PLANET 5. Union старых
версий в типах относится к сохранённым snapshot/test seam и не является
HTTP negotiation с предыдущим клиентом. Выпуск клиента и сервера согласованный.

MCP-инструменты не меняют свои аргументы или полномочия: каждый проектный
вызов содержит явный `countryId`. Статус, перенос и удаление терминала идут
через существующие task-инструменты, транзакционное событие и WebSocket.
Повтор `idempotencyKey` не создаёт второй рейс или повторное событие.
Пассажиры — ограниченные сессионные жители, не задачи и не новые записи работы.

Ответ использует ETag и `Cache-Control: private, max-age=60,
stale-while-revalidate=600`. Комментарии и невизуальные поля snapshot не
инвалидируют; визуально значимые события пересобирают компактную проекцию.

Связанный внутренний `GET /api/tasks/search` возвращает для каждого здания не
только `cityId`/`cityName` и `origin`, но также `cityCenter` и `cityBounds`.
Браузер использует viewport города, чтобы результат поиска из другой части
страны сначала открыл правильный город, а затем сфокусировал здание.

## Быстрое подключение

1. В Tasktopia откройте кнопку «MCP-интеграции» или «Подключить MCP».
2. Скопируйте URL `https://tasktopia.online/mcp`.
3. Создайте персональный ключ с минимально необходимыми scopes.
4. В MCP-клиенте выберите Streamable HTTP и передайте `Authorization: Bearer <ключ>`.

Ключ нельзя добавлять в query string или хранить в открытом конфигурационном файле. Используйте secret storage клиента. Каждый метод `/mcp` требует действующий Bearer-ключ; запрос без него получает `401` и стандартный `WWW-Authenticate: Bearer` challenge.

```json
{
  "mcpServers": {
    "tasktopia": {
      "url": "https://tasktopia.online/mcp",
      "headers": { "Authorization": "Bearer ttp_mcp_..." }
    }
  }
}
```

Ключ создаётся в разделе MCP и показывается только один раз. В PostgreSQL хранится только SHA-256 hash. Новый персональный ключ отзывает предыдущий активный ключ пользователя, а команды выполняются от его имени в явно указанной стране. Принимается только точный заголовок `Authorization: Bearer ttp_mcp_...`: `X-API-Key`, bare token, cookie и query-параметры отклоняются. Эти персональные ключи не являются OAuth-токенами, поэтому endpoint не публикует фиктивный OAuth discovery.

При выпуске выбираются срок `30 | 90 | 365` дней и непустое подмножество scopes:

- `country:read` — страны, города, районы и MCP resources; полный `city.get` дополнительно требует `tasks:read` из-за списка задач;
- `cities:write` — профиль страны и Государственный архив, создание, обновление, переименование и безопасное удаление городов;
- `districts:write` — создание, обновление, переименование, смена состояния и безопасное удаление районов;
- `tasks:read` — чтение задач, записей архива и состояния фоновых операций `task.*`;
- `tasks:write` — создание/уточнение задач и связанных дефектов, перенос между спринтами одного города, назначение, смена стадии и безопасное удаление задач;
- `comments:write` — добавление комментариев.

Глава страны и министр могут выбрать любые scopes. Наблюдателю доступны только `country:read` и `tasks:read`. `country.list` не требует контекста; каждый другой MCP tool принимает обязательный `countryId`. Сервер заново проверяет членство и текущую роль пользователя именно в этой стране на каждом вызове, поэтому `countryId` нельзя использовать для обхода доступа, а страна, выбранная в веб-интерфейсе, не влияет на MCP. Истёкший, отозванный, повреждённый или пустой по разрешениям ключ отклоняется. Существующие ключи с `expires_at = NULL` продолжают работать до отзыва; все новые имеют явный срок.

## Ограниченные чтения структуры

Для навигации используйте `view: "compact"` у `country.list`, `city.list`,
`district.list` и `archive.record_list`. Ответ содержит `kind`, `version: 1`,
`items`, `nextCursor` и, кроме списка стран, `countryId`. Соответствующие `kind`:
`country.list-page`, `city.list-page`, `district.list-page`, `archive.record-page`.
`limit` по умолчанию 50, допустим от 1 до 100; `cursor` и `limit` применяются
только в compact-режиме. Продолжайте до `nextCursor: null` с прежним контекстом.
Порядок — `createdAt ASC, id ASC`; cursor сохраняет точность PostgreSQL timestamp
и связан с видом списка, аккаунтом для стран, страной и необязательным `cityId`
для районов. Чужой или несовместимый cursor отклоняется.

Метаданные стран не включают длинный паспорт проекта; города содержат счётчики
районов и задач, районы — агрегированный `workload` без `cells`/`lots`, архив —
`bodyLength` без `body`. Полный текст одной записи читает
`archive.record_get(countryId, recordId)` с `tasks:read`.

`country.get` с `view: "compact"` возвращает `kind: "country.card", version: 1`:
полный паспорт страны, архив и `counts.cities`, без списка городов.
`city.get` с этим режимом возвращает `kind: "city.card", version: 1` с метаданными
и счётчиками города, без задач и геометрии районов; достаточно `country:read`.
Полный `city.get` требует также `tasks:read`. Отсутствие `view` или `view: "full"`
сохраняет прежние полные формы и массивы без усечения.

Обычный путь агента: выбрать страну через compact-список, прочитать её compact-карточку,
найти город/район страницами, затем использовать `task.list_page`, compact-карточку
задачи и только нужные коллекции/документы. Инструменты возвращают JSON без декоративных
отступов; `structuredContent` сохраняет те же данные.

## Ограниченные чтения задач

Прежние `task.list`, `task.get` и `GET /api/tasks/:taskId` сохраняют полный ответ.
`task.get` с `view: "compact"` возвращает отдельный контракт `kind: "task.card", version: 1`:
основные поля, описание, критерии, геометрию, аккаунты, реальные `counts` и не более
50 `documentMetadata`. Длинные Markdown-материалы, MR и дочерняя история в карточку
не входят. Документы имеют `isFilled` и `contentLength`, но не `content`.

`task.collection_list` принимает `countryId`, `taskId`, `collection`, необязательные
`limit`, `cursor`, `order`. Доступные коллекции: `comments`, `events`, `defects`,
`attachments`, `documents`, `checklist`, `dependencies`, `mergeRequests`.
Ответ `kind: "task.collection-page", version: 1` содержит `items` и `nextCursor`.
Документы и чек-лист по умолчанию идут по позиции, зависимости по номеру, история
по времени от новых к старым. Второй ключ — ID (у MR — URL). Cursor сохраняет
точность PostgreSQL timestamp и связан со страной, задачей, коллекцией и порядком.
Последняя страница имеет `nextCursor: null`.

`task.list_page` возвращает `kind: "task.list-page", version: 1` и короткие записи
со статусом и местоположением. Можно совместить `q`, `cityId`, `districtId`, `status`,
`workItemType`, `priority`, `assigneeUserId`; порядок — `updatedAt DESC, id DESC`.
Cursor нельзя использовать с другим набором фильтров или страной. Размер страницы
у обоих инструментов по умолчанию 50, допустим от 1 до 100. Для содержимого одного
документа используйте `task.document_get(countryId, taskId, documentId)`.
Все новые инструменты требуют `tasks:read` и проверяют актуальное членство.

Внутренние read-only HTTP endpoints требуют явный query `countryId` и дают
`Cache-Control: private, no-store`:

| Endpoint | Ответ |
| --- | --- |
| `GET /api/tasks/:taskId/card` | `TaskCardDto` |
| `GET /api/tasks/:taskId/collections/:collection` | `TaskCollectionPageDto`, query `cursor`, `limit`, `order` |
| `GET /api/tasks/:taskId/documents/:documentId` | Один полный `TaskDocumentDto` |
| `GET /api/tasks/list-page` | `TaskListPageDto`, те же фильтры и cursor |

У `task.add_comment`, `task.set_status`, `task.report_progress` и `task.transfer` необязательный
`resultMode: "compact"` возвращает отдельный `kind: "task.command-result", version: 1`
с номером, заголовком, статусом, прогрессом и короткими полями задачи. Режим по
умолчанию `full` сохраняет прежний ответ. Compact comment/progress не собирают
все комментарии, события и документы; проверки чек-листа, дефектов и назначения
владельцу токена остаются обязательными. `resultMode` — только выбор представления,
он не входит в command payload/hash. Retry с другим режимом не создаёт новую команду.

## Фоновые пространственные команды

`city.create`, `district.create`, `task.create`, `country.regenerate`,
`task.set_status` (также `task.report_progress`), `task.transfer`, `task.delete`,
`city.delete`, `district.delete` и `district.complete` сначала сохраняют durable job
с уникальным `(country, operation, idempotencyKey)`. MCP ограниченно ждёт результат.
Если worker успел завершить команду, возвращается прежний результат в выбранном
режиме; если ожидание превысило `GENERATION_WAIT_MS`, вызов остаётся успешным и возвращает:

```json
{
  "status": "accepted",
  "job": { "id": "<uuid>", "operation": "task.create", "status": "PENDING" }
}
```

Актуальный worker сохраняет внутри страны порядок `createdAt, id`: следующая команда не обгоняет уже выполняющуюся. Между странами учитывается время последнего обслуживания, поэтому большой backlog одной страны не занимает все последовательные ходы. Истёкшая последняя попытка проверяет уже committed receipt: подтверждённый результат восстанавливается, иначе job становится FAILED. Ожидания coalesce по job, получают PostgreSQL notification и используют ограниченный SQL fallback.

Migration `0046` добавляет внутренние состояния `QUEUED`/`EXECUTING` для шести новых
операций; публично они остаются `PENDING`/`RUNNING`. Старый worker их не захватывает
и не выполняет как другую команду. При смешанной версии или откате новые команды
ждут актуальный worker; строгий общий FIFO при старом worker не гарантируется.
Данные и durable jobs при таком откате сохраняются.
Migration `0047` сохраняет исходную сериализацию новых команд до JSONB-проекции,
чтобы retry прежних синхронных receipts не менял hash из-за порядка ключей.
Исторические receipts и их hashes не переписываются.

Это не ошибка и не повод повторять write с новым ключом. Опрашивайте `world_generation.get` с тем же `job.id`; `COMPLETED` содержит `result`, окончательный `FAILED` — безопасные `error.code/message`. Повтор исходной команды с тем же idempotency key и тем же payload возвращает тот же job/result; другой payload даёт `CONFLICT`.

Polling проверяет актуальное членство и право чтения самой операции: `task.*`
требует `tasks:read`, операции страны/города/района — `country:read`. Право записи
само по себе не даёт права polling. Публичные accepted/polling-ответы не содержат
входной `payload`. Для `GENERATION_FAILED`, включая исторические записи, сообщение
фиксировано: «Генерация завершилась с ошибкой». Неожиданные ошибки MCP resources
также не раскрывают внутренние сообщения сервера.

У `world_generation.get` необязательный `view: "compact"` возвращает для завершённых
`task.create`/`task.set_status`/`task.transfer` короткий `task.command-result`
без комментариев, документов и истории.
Другие результаты сохраняют форму. По умолчанию polling возвращает полный результат;
изменение `view` или `resultMode` на retry не меняет payload и не повторяет команду.
Accepted подтверждает постановку в очередь: проверки текущего состояния объекта и
точного подтверждения удаления выполняет worker; их отказ становится `FAILED`
без частичной мутации.

Закрытие HTTP-соединения ожидающего клиента снимает только его ожидание и observer,
если других ожидающих нет. Уже сохранённая команда остаётся в очереди и может
завершиться после отключения; используйте прежний ключ или polling. Сигнал отмены
не сохраняется в payload и не отменяет SQL-транзакцию worker.
Если сигнал уже отменён до enqueue, возвращается `CANCELLED` без нового job.

Перед записью и сравнением payload приводится к JSON-совместимой форме: необязательные object-поля со значением `undefined` считаются отсутствующими, а явный `null` остаётся значимым значением. Поэтому обычный `task.create` без `dueAt`, назначения или park-полей не отличается от сохранённого JSONB и не вызывает ложный `CONFLICT`.

## Минимальный сценарий

Создать город:

```json
{
  "countryId": "<uuid страны>",
  "name": "Northpoint",
  "description": "Основной продуктовый город",
  "idempotencyKey": "northpoint-v1"
}
```

Создать и активировать район:

```json
{
  "countryId": "<uuid страны>",
  "cityId": "<uuid города>",
  "name": "Release Quarter",
  "goal": "Подготовить релиз",
  "capacitySp": 14,
  "archetype": "NEW_BUILD",
  "activate": true,
  "idempotencyKey": "release-quarter-v1"
}
```

`archetype` необязателен: `NEW_BUILD | PRIVATE | MIXED_URBAN | COMMERCIAL | CIVIC`. `PRIVATE` сохранён как стабильный legacy-код и теперь означает район низко- и среднеэтажных ЖК; `NEW_BUILD` означает средне- и высокоэтажные ЖК. Отдельных частных домов в активном каталоге нет. Без архетипа сервер выводит тип из названия/цели района, morphology города и уже существующей застройки. Архетип влияет на участки и автоматический выбор зданий.

`capacitySp` — только положительный ориентир нагрузки. Сервер не блокирует задачи при его превышении: допустимая загрузка зависит от длительности итерации, размера команды и распределения исполнителей. `district.list`, `city.get`, `task.create` и `task.delete` возвращают `workload`: ориентир `targetSp`, общую оценку `plannedSp`, незавершённую `openSp`, число задач и `overTargetBySp`. MCP-агент показывает эти данные пользователю, но не создаёт новый район без его решения.

Удаление использует отдельные destructive-инструменты и точное подтверждение текущего названия: `task.delete` принимает `confirmTitle`, а `district.delete` и `city.delete` — `confirmName`. Прежние площадки задач остаются заняты постоянными руинами с краткой историей и никогда не используются повторно. Удаление города сохраняет эту историю на уровне страны; удаление самой страны очищает её вместе с остальными данными. Активный удалённый район передаёт активность следующему плановому.

### Перенос в другой спринт

`task.transfer` требует `tasks:write`, действующее членство с ролью OWNER/MEMBER и явный `countryId`. Это отдельная операция, а не изменение `districtId` через `task.update_fields`:

```json
{
  "countryId": "<uuid страны>",
  "taskId": "<uuid существующей задачи>",
  "targetDistrictId": "<uuid другого спринта того же города>",
  "comment": "Перенос в следующую итерацию",
  "idempotencyKey": "task-transfer-next-sprint-v1"
}
```

`comment` необязателен, до 4000 символов; остальные поля обязательны. Схема строгая: неизвестные поля отклоняются. ID, номер, статус, история и служебная роль задачи сохраняются. Прежний участок освобождается, новый выбирается автоматически в целевом районе. Оба изменения и запись истории атомарны; ошибка размещения откатывает перенос. Повтор с прежним ключом не выполняет перенос повторно. Перенос в другую страну/город или завершённый/заброшенный район запрещён.

Ответ содержит актуальную задачу и канонический `url` вида `/task/<number>?countryId=<uuid>&taskId=<uuid>`. Такие же ссылки возвращают `task.get`, `task.create` и операции ссылок: номер локален стране, а UUID сохраняется после переноса. Браузерный эквивалент — `POST /api/tasks/:taskId/transfer` с тем же телом без `countryId` (страна берётся из авторизованного активного контекста). [Полный контракт постоянных площадок](PERMANENT-TASK-SITES.md).

Добавить задачу в активный район:

```json
{
  "countryId": "<uuid страны>",
  "cityId": "<uuid города>",
  "title": "Открыть районную аптеку",
  "description": "Каталог, поиск и карточка лекарства",
  "workItemType": "TASK",
  "acceptanceCriteria": "Основные сценарии и ошибки покрыты проверками",
  "estimate": 3,
  "priority": "HIGH",
  "assigneeEmail": "member@example.com",
  "assigneeRole": "backend-lead",
  "forUserEmail": "product-owner@example.com",
  "idempotencyKey": "task-pharmacy-v1"
}
```

`districtId` у `task.create` необязателен: без него используется активный район города. Здание подбирается автоматически под свободный участок. Каталог зданий описывает визуализацию мира и не задаёт параметры создания задачи.

`assigneeEmail` необязателен, но указанный человек должен быть зарегистрирован и состоять в правительстве переданной страны. `assigneeRole` фиксирует роль исполнителя в конкретной работе (`backend-lead`, `qa`, `ai-agent:codex`), а `forUserEmail` — зарегистрированного заказчика/владельца результата. Создателем задачи автоматически становится владелец персонального MCP-ключа; создатель, исполнитель и заказчик могут различаться. Назначение и роль можно позже изменить через `task.assign`, заказчика — через `task.update_fields`.

Материалы реализации хранятся как документы задачи. После создания агент
заполняет `system-analysis.md`, `architecture.md`, `design-system.md` и
`implementation-plan.md` через `task.document_upsert`; при необходимости
добавляет другие kebab-case `.md`. По согласованному плану агент вызывает
`task.checklist_replace`, а по ходу работы отмечает пункты через
`task.checklist_item_update`. Человек просматривает документы, чек-лист, MR и
историю в карточке. Рабочие изменения, включая перенос между спринтами,
выполняются через MCP; интерфейс служит для просмотра и навигации.

Зависимости задаются через `task.dependency_add/remove` только между задачами
одного города. Commit, MR/PR, CI run и другие постоянные HTTP(S)-артефакты
связываются через `task.link_add/remove`. Логи, скриншоты и другие файлы агент
передаёт через `task.attachment_add` как полный стандартный Base64 с padding,
без пробелов, префикса `data:` и посторонних символов. Декодированный файл
должен быть непустым и не превышать `MAX_ATTACHMENT_BYTES` (по умолчанию 10 MiB).
Для одинакового повтора используются те же аргументы и `idempotencyKey`:
содержимое проверяется по SHA-256, поэтому
другие байты даже той же длины возвращают `CONFLICT`. Для ключей, сохранённых
до этого изменения, одинаковый повтор проверяет файл на диске и обновляет
receipt без нового вложения или события; недоступный файл возвращает `CONFLICT`.
Откат загрузки удаляет её файл. Удаление вложения или каскадное удаление задачи,
района и города очищает файлы после commit, сохраняя их при rollback.
Полная хроника доступна через `task.activity`.

`country.update_profile`, `city.update`, `district.update` и `task.update_fields`
меняют только переданные поля и сохраняют ID. Пустая строка очищает текст,
`deadline: null`/`dueAt: null` снимает дату. Тип задачи:
`TASK | BUG | RELEASE | HOTFIX`. Связанные наблюдения создаются отдельно через
`task.defect_create` с шагами, фактическим и ожидаемым результатом, а затем
ведутся `task.defect_update` по отдельному циклу `OPEN → IN_PROGRESS → VERIFYING → FIXED`.
Во время обычного исправления родительская задача остаётся в `TESTING` со своим
прогрессом; завершение задачи блокируется, пока любой связанный дефект не `FIXED`.

Отправить прогресс:

```json
{
  "countryId": "<uuid страны>",
  "taskId": "<uuid задачи>",
  "status": "IN_PROGRESS",
  "progress": 55,
  "comment": "Основной сценарий готов, завершаем обработку ошибок",
  "idempotencyKey": "task-pharmacy-progress-55"
}
```

Допустимый порядок:

`PLANNING → STARTED → IN_PROGRESS → TESTING → COMPLETED`

Пропуск стадий запрещён. Возврат разрешён только `TESTING → IN_PROGRESS` и требует комментарий.

Значения прогресса по умолчанию: планирование `0%`, начало работы `0%`, работа `50%`, тестирование `90%`, завершение `100%`. Явный процент внутри допустимого диапазона стадии сохраняется.

## Надёжность

Номер задачи монотонен в пределах страны и не переиспользуется после удаления. Additive migration `0043` учитывает живые задачи, постоянные площадки, прежние receipts и вложенную историю событий. PostgreSQL allocator защищает также старый образ с `MAX(active)+1` при rollback; явное восстановление старых номеров доступно только доверенному SQL `SET LOCAL tasktopia.preserve_task_numbers=on`, не MCP.

Все изменяющие операции требуют уникальный `idempotencyKey`. Повтор с тем же payload возвращает результат без новой команды; тот же ключ с другим payload даёт `CONFLICT`. Пространственные операции, которые уже перечитывали актуальный объект на retry, сохраняют новые bounded v2 reference receipts (`receiptVersion`, `entityKind`, `entityId`, `id`, номер задачи); старые hash/rows не переписываются. Такие retry возвращают актуальный объект в выбранном режиме. Остальные старые receipts сохраняют прежний исторический ответ. Команда, размещение объекта, событие и idempotency result сохраняются одной PostgreSQL-транзакцией с блокировкой строки страны, поэтому конкурентные изменения геометрии не пересекаются.

Каждое изменение увеличивает `worldVersion` и создаёт событие. Создание задачи, смена стадии, комментарий и назначение ответственного также попадают в неизменяемую хронику с аккаунтом автора. Веб получает `world:event` через Socket.IO. Пространственные события содержат `payload.affectedBounds` (`minX`, `minY`, `maxX`, `maxY`), поэтому клиент перечитывает только пересекающиеся чанки. Открытый план повторяет только свои scoped-запросы; структурные изменения перечитывают лёгкий bootstrap со счётчиками и bounds. Если границы отсутствуют, применяется безопасная полная инвалидация резидентных чанков.

Внутренний session-auth endpoint `/api/chunks/:x/:y?lod=overview|detail` отдаёт компактный `ChunkPayloadDto` клиенту, запросившему vendor `Accept` version 2: terrain и decorations детерминированно восстанавливаются браузерными Worker'ами. На rollout-окно запрос без vendor-заголовка получает полный render-ready `ChunkDto` для совместимости с уже открытой вкладкой предыдущего релиза; ETag разделён по representation и ответ содержит `Vary: Accept`. Ответ приватный; актуальная версия события передаётся отдельно в `X-World-Version`, включая 304. Endpoint не является MCP resource/API для внешних агентов.

Ресурсы:

- `tasktopia://countries/{countryId}`
- `tasktopia://catalog/buildings`

Оба ресурса требуют `country:read`.

Проверка живого сервера:

```bash
npm run seed
npm run dev
npm run smoke:mcp
```

Локальный `npm run seed` ограничен одним городом, 10 районами и 30 задачами,
чтобы проверка MCP не зависела от тяжёлой showcase-генерации.


## Интерфейс читает, MCP управляет работой

Создание и изменение задач, стадий, прогресса, исполнителей, комментариев и
чек-листов выполняются через MCP. Не предлагайте пользователю искать в интерфейсе
кнопку «Взять в работу»: карточки, документы и карта служат для просмотра и навигации.
При `PLANNING → STARTED` через `task.set_status` или `task.report_progress` задача
без исполнителя атомарно назначается авторизованному владельцу MCP-токена.
Существующее назначение сохраняется; явная передача выполняется через `task.assign`.
Открытие карточки, комментарий и изменение описания не назначают исполнителя.
`actor` и `assigneeRole` не заменяют подтверждённую учётную запись. Общий токен
означает общего владельца; не выдавайте его за отдельную личность агента.
Настройки аккаунта и состояние прочтения уведомлений не изменяют задачи.

## Короткие изменения в истории

Новые task audit events дополнительно содержат `details.changes`:
`[{field,before,after}]`. Разрешены только `title`, `status`, `progress`, `priority`,
`estimate`, `dueAt`, `workItemType`, `assignee`. Длинные описания, критерии и Markdown
в before/after не копируются. Прежние `from`, `to`, `changedFields`, `fromUserId`,
`toUserId` сохраняются, старые события без changes остаются читаемыми.

У `assignee` values — UUID/null, а `beforeLabel`/`afterLabel` при наличии содержат
снимок настоящего имени участника не длиннее 60 символов, без email. В интерфейсе
нужно использовать labels либо «Назначен»/«Не назначен», а не UUID. Начало работы
по-прежнему назначает только владельца авторизованного токена и не заменяет уже
имеющегося исполнителя; новые метаданные не меняют личность или полномочия.

Личные read-only новости и альбом используют реальные durable events, явную
страну, актуальные права и pagination. [Контракты и совместимость](PRODUCT-STATE-DELIVERY-2026-09-25.md#расширение-2026-10-16-личные-события-и-альбом).
