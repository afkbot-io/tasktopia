# Сцена города между перезапусками сервера

Задача 82: `9d6ac69f-7fad-4f0f-a68e-ce94e4595fb8`, страна
`4201d605-751a-469b-8d5f-a7e322a7ece1`. База — `57281e9d`.
Это часть общего плана живого города; общий релиз ещё не выполнен.

## Причина и поведение

Итоговый замер прежнего сервера на сохранённом городе с 10 000 задачами,
одним районом и 576 chunks дал первое открытие desktop 7 460,5 мс при
бюджете 5 000 мс. Повторные открытия занимали 17–22 мс. Профиль отдельно
показал 3 649 мс на построение authenticated scene; сериализация и сжатие
не объясняли основную задержку. Замер сохранён как не прошедший бюджет.

Новая additive-таблица `0049` хранит одну текущую производную сцену на город.
Она не заменяет задачи, размещения, дороги или транспортные планы. После
отдельного прогрева новый процесс той же сборки читает готовую сцену без
повторного построения chunks. Пустой кэш, новая версия мира, новая сборка
или повреждённая запись запускают прежний конструктор. После успешной
транзакции результат становится доступен следующим процессам.

Это не обещание ускорить первую в истории полную сборку. На native fixture
отдельные процессы preview/write/repeat заняли 3 250 / 3 773 / 374 мс;
первые два строили сцену, третий прочитал готовую. Прогрев требуется после
последнего maintenance транспорта и дорог, до клиентской приёмки.

## Согласованность и границы доступа

Ключ включает world version, scene schema, asset revision, app version и
манифест согласованной сборки. `npm run build` пишет `dist/runtime-build.json`
после успешной сборки server и scene CLI. Оба исполняемых файла сверяют свои
SHA и SHA второго файла с манифестом. Частичная или смешанная сборка не
переиспользует снимки; CLI отказывает. Production source TS также не пишет
снимки. В dev/test пространство ограничено процессом.

Манифест проверяет согласованность файлов, не является подписью или SCM
approval. Нельзя вручную пересоздать его поверх смешанных файлов и считать
это проверенным релизом. В контейнер копируется весь `dist` одной сборки.

Базовая сцена не содержит личных rail/sea connections. Membership и
city/country проверяются при каждом запросе, затем отдельно строятся
разрешённые связи текущего viewer. Даже внутренний read выполняется в одном
MVCC snapshot. Persisted write участвует в той же транзакции; process LRU
публикуется только afterCommit и сохраняет прежние ограничения 8 записей /
1 024 страниц. Старый world version не перезаписывает более новый.

Blob ограничен 64 МиБ, распакованные данные — 128 МиБ. Zstd работает
асинхронно с пределом выходного размера. Длина, SHA, schema, city ID,
chunk size, published version и отсутствие viewer fields проверяются до
повторного использования. Повреждённая запись даёт обычную сборку. Ошибка
БД остаётся ошибкой, а не маскируется под cache miss. При удалении города
или страны blob удаляется каскадно. История снимков не накапливается.

## Проверка

`scene82-regression-v6.log`: 34 проверки в 8 файлах. Public RED→GREEN
подтверждает fresh service без построения chunks, внутренний MVCC read и
запрет сохранять viewer-specific response. Проверены изменение настоящей
задачи, более старый writer, два принудительно конкурентных cold readers,
откат без публикации в память/БД, отзыв membership, чужой город с валидным
checksum, повреждение blob/hash/build, byte limits и оба cascade delete.
Независимые geometry oracle явно отключают кэш конструктора.

CLI проверяется в отдельных скомпилированных процессах: preview/write/repeat,
conservation, scope/arguments и отказ смешанным server/CLI artifacts. На
сохранённом native10000 checksum геометрии остаётся
`61f5181de2409c271acace539177a56729554f42138e961b7afb4d103c2c7fa0`;
576 chunks и вся работа/геометрия/версия мира сохранены. Компактная базовая
сцена — 37 707 546 байт, zstd — 3 371 940. Authenticated response добавляет
прежние 41 байт пустых personal connections, HTTP-контракт не меняется.

Scoped cold gate использует неизменные официальный observer и настройки
профилей, отдельный явный прогрев и новый web процесс для каждого профиля.
Первый browser CITY: desktop 2 708,82 мс / mobile 23 623,21 мс — оба в
прежних бюджетах 5 000 / 30 000 мс. Mobile: 393×851, DPR2,75, CPU×4,
1,6 Мбит/с и 60 мс задержки. Headers 780 / 686 мс; один scene GET,
10 000 задач, 576 chunks, прежние decoded bytes, ошибок приложения нет.
Это аппаратный Chromium/Metal на Mac, не физический телефон.
Доказательства — `scene82-native-qualification-v1.json` и
`scene82-native-cold-v1.json`; ошибка первого setup с неверным именем
таблицы событий сохранена отдельно и не выдана за продуктовый отказ.

`scene82-build-v2` проходит; после добавления только тестов и документации
проходят `scene82-types-final-v7`, `scene82-lint-final-v7` и diff check.
AI/security review фиксированного diff от `57281e9d`: открытых замечаний
нет. Проверены ACL/MVCC/monotonic upsert, commit hooks, byte/decode limits,
приватность base scene, build provenance, cascade и откат additive DDL.
Это локальное AI-review, не SCM approval.

Это отдельный server slice; он не уменьшает память клиента.
Цель 256 МиБ ещё не достигнута. Полный browser journey, SCM CI и managed
release общей цели не подменяются scoped cold-проверкой.

## Выпуск и откат

Применить additive `0049` штатным мигратором. Из точного собранного образа
выполнить `node dist/synchronize-city-scenes.mjs --country <UUID>` сначала
без записи, затем с `--write` и повторно с `--write`. Можно ограничить
`--city <UUID>` перед `--write`. Команда требует `NODE_ENV=production` и
`DATABASE_URL`, не применяет DDL и не перегенерирует мир. Проверить `ready`
для всех выбранных городов; на повторе `constructed: 0`, `changed: 0`,
сохранность canonical checksum/world version. Затем проверить свежий web
процесс и первый клиентский вход. Не публиковать секретный URI в логах.

Порядок — в [runbook](../DEPLOYMENT.md). Прежний совместимый образ игнорирует
новую таблицу; данные работы миграция не меняет, старые checksum не правятся.
Снимок расходный: новая сборка сама не принимает старое пространство.
Удаление производной записи не требует регенерации города, но следующий
cache miss вновь платит полную стоимость конструктора. Это не отменяет
проверки совместимости и восстановления всего общего релиза.
